# Протокол итерации

## Роли
- **Человек** — единственный, кто пишет в репозиторий. Переносит файлы, коммитит, ставит теги, принимает финальные решения.
- **Оркестратор (чат-ИИ)** — читает репозиторий по GitHub, планирует, формулирует TASK.md, принимает REPORT.md.
- **Агент (Qwen)** — работает в песочнице, исполняет TASK.md, формирует REPORT.md.

## Цикл одной итерации

1. **Старт.** Человек открывает новую сессию чата, вставляет `ORCHESTRATOR_SYSTEM.md` + ссылку на репозиторий. Оркестратор читает состояние → выдаёт TASK.md.
2. **Человек** открывает сессию Qwen-агента, вставляет `AGENT_SYSTEM.md` + ссылку на репозиторий + TASK.md. **Файлы контекста агенту не передаются — он читает их сам.**
3. **Агент** проводит обязательный ритуал старта → подтверждение понимания → работа в песочнице → REPORT.md + файлы/патчи.
4. **Человек** переносит файлы из песочницы в репозиторий (или применяет патч), коммитит, ставит тег `iter-NNN`.
5. **Человек** возвращается к Оркестратору: «итерация NNN закоммичена, тег стоит».
6. **Оркестратор** читает новый коммит, тег, REPORT.md → сверяет REPORT.md с реальным diff → приёмка → новый TASK.md или замечания.
7. **Человек** принимает финальное решение.

## Что важно в новой архитектуре

- **Единый источник истины — репозиторий.** И Оркестратор, и агент читают из него. Расхождения возможны только между «что человек закоммитил» и «что агент сделал в песочнице» — это и есть предмет приёмки.
- **Человек не передаёт контекст, он передаёт артефакты.** Если агент просит «пришли мне файл X» — это сигнал, что либо он неверно прочитал TASK.md, либо в репозитории что-то не так. Такое стоит разбирать, а не удовлетворять молча.
- **Сверка REPORT.md с diff — обязанность Оркестратора.** Если агент пишет «изменено 3 файла», а в коммите 5 — это повод вернуть итерацию. Раньше Оркестратор не мог это проверить, теперь может.
- **Агент сам отвечает за актуальность базовой точки.** В REPORT.md есть «Базовая точка (тег/коммит)» — если он работал от устаревшего состояния, это видно.

## Ветки и теги
- Рабочая ветка — `main`.
- После каждой принятой итерации человек ставит тег `iter-NNN` (аннотированный, с 1 строкой описания).
- Если итерация экспериментальная и рискованная — человек создаёт ветку `exp/NNN-краткое-имя` вручную, работает в ней, затем merge или abandon.

## Коммиты
- Формат: Conventional Commits (`feat:`, `docs:`, `refactor:`, `fix:`, `chore:`).
- Тело коммита: `iteration: <ID>` + 1–2 строки сути.
- Один коммит = одна итерация. Если итерация большая — разбивайте по логическим блокам, но с общим префиксом `iter-NNN:`.

## Правила безопасности
- Перед `git push --force` (даже в свою ветку) — остановиться и подтвердить у себя, что тег с последней хорошей точкой существует.
- Перед удалением любого файла в репозитории — проверить, что он не упомянут в `PROJECT_MAP` или `CHECKPOINT` как важный.
- Секреты и токены — никогда в промпты агента/оркестратора, только через `git config` локально.

## Чек-лист человека перед запуском итерации
- [ ] Прошлая итерация принята (или явно отложена).
- [ ] Тег `iter-<прошлая>` стоит на коммите.
- [ ] В TASK.md заполнены все секции, нет плейсхолдеров.
- [ ] Scope и «Вне scope» непротиворечивы.
- [ ] DoD проверяем (можно ответить да/нет по каждому пункту).
